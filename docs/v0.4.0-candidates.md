# v0.4.0 — candidate list

Collection stage. **Nothing here is decided**, and the list is not yet scoped to
one release. Each entry gets a verdict (in / out / later) and an effort estimate
in the validation pass that follows. Written up front so the validation argues
against a fixed list instead of a moving one.

Context check on 2026-07-28: no GitHub issues, no PRs. The forum thread has since
grown to 18 posts — `pyspilf` (Sandro) replied to the v0.3.0 announcement after
installing it, and his post settles one open decision and reports one wording
bug. See "From the thread" below; it changes the order.

## From the backlog (`CLAUDE.md`)

**A. Stable cluster IDs.** The ID is `f"{lat:.2f}/{lon:.2f}"` (`api.py`), so a
centroid drifting across a 0.01° boundary destroys the entity and creates a new
one — history lost. Fix: match new clusters against the previous cycle within the
cluster radius and carry the ID forward. Prerequisite for anything that reasons
about "the same place over several days".

**B. Ignore zones for persistent heat sources.** Raised independently by two
users (finity, posts #4/#5). Manual zones (coordinate + radius) in the options
flow, same map picker as the main radius. The *automatic* variant — hide a spot
seen on many consecutive days — is proposed to stay out: it silently decides a
fire is not a fire, and a real multi-day front looks exactly like a factory. The
design-line-compatible half is to expose the observation as a fact
(`days_seen`) and let the user hide it. Depends on A.

**C. FRP-driven marker colour + intensity attribute.** Mechanism proven in
v0.3.0 (the `entity_picture` route), so this is swapping one module constant for
a handful of pre-built pictures. Blocked on a maintainer decision: the
thresholds, and whether the attribute is called `severity` (reads as a risk
verdict) or `intensity` (describes radiative power, which is what it is).

**D. Radius cap and visible truncation.** The location selector has no upper
bound; past a certain size `FETCH_COUNT = 1000` truncates the result and the only
signal is a log warning. Cap the radius, surface the truncation on the sensor, or
both.

**E. Entry identity on geo_location entities.** Every fire carries
`source: nasa_firms` regardless of which config entry produced it, so a map card
using `geo_location_sources` mixes two locations — and each entity's state is the
distance from *its own* origin, so foreign fires read as plausible wrong numbers.
Add an entry-identifying attribute so `auto-entities` can filter. Not a change to
the source string: that is documented and would break existing configs.

## From the maintainer (2026-07-28)

**F. Move documentation into the GitHub wiki.** The README is 334 lines / ~2500
words across 13 sections — installation, setup, entity reference, a full
dashboard example, templates, limitations, roadmap, credits. Too much for a
landing page. Open questions for validation: what stays on the front page as the
"why and how do I install it" pitch, what moves; whether a wiki hurts the HACS /
Core story (Core expects docs in the HA docs repo, and a wiki is not
version-pinned to a release); whether the dashboard recipes are better served as
files in `docs/` than as wiki pages.

**G. Better map / fire view, with the wind shown on it.** The map is where users
actually look, and today it shows undifferentiated flame markers carrying
neither intensity nor wind. Overlaps with C: both go through the one thing the
map card honours for source-fed entities, the `entity_picture`, so the same
generated image can carry intensity *and* a wind arrow.

The constraint that decides the shape of this: **wind is fetched for the nearest
fire only** — one met.no request per 15-minute cycle, a hard design rule from
v0.3.0 that exists so a busy bounding box does not fire off hundreds of requests.
So either only one marker on the map can ever carry an arrow, or the rule has to
be renegotiated (e.g. wind for the N nearest fires, or one lookup for the whole
box on the assumption that wind is regional). That decision comes before any
drawing work.

**H. Configuration and general UX.** Umbrella item, deliberately vague at this
stage: the config and options flow, what the entities look like on first
install, how much a new user has to understand before the integration is useful.
Needs to be broken into concrete, verifiable items during validation, or it
becomes an unshippable "make it nicer".

## From the thread (pyspilf, post #18, 2026-07-28)

First real feedback from someone running v0.3.0. Three things come out of it.

**I. The wind sentence in the README card is worded wrong.** He reports the card
telling him a fire lies to the **ENE** while the wind is **from the SSW** — and
being called "sideways **to your position**", when that geometry pushes the smoke
away from him. He is right about the physics, and the card is right about the
number: verified both ways, the offset is exactly **135°**, and the card's
bracket is `off <= 135` → "sideways to your position". So the maths is sound and
the *label* is the defect — "to your position" asserts movement toward the reader
that 135° does not support.

The first fix was the wording alone — "past you to one side", plus the raw
offset in brackets — on the reasoning that widening "away from you" would make
the card say the reassuring thing more often, and that being wrong toward
caution is the acceptable direction.

**That reasoning was wrong, and he corrected it with a sketch.** At 135° the
component of the smoke's movement along the line to the reader is
cos(135°) = −0.71: *71% of the drift is leaving*. Calling that "past you to one
side" is not a cautious reading, it is an inaccurate one, and a card that
contradicts what a user can draw on paper loses its authority for every other
line it prints.

The brackets are therefore the equal thirds of the half-circle, 60° and 120°,
where the along-the-line component is exactly ±half the wind speed. *Towards*
means more than half the drift is coming at you, *away* means more than half is
leaving. Note this is **not** simply the softer option: the "towards you"
bracket grows from 45° to 60° as well, so the card warns in more cases than
before, and the undecided middle shrinks from 90° of arc to 60°.

This is a **README-only defect**. The integration's attributes are correct; the
card is documentation. It needs no release and should be fixed immediately,
ahead of everything else here, because it sits exactly on the line the project
has been careful about and a user has already misread it.

**J. The FRP thresholds for C are effectively answered.** He ran a four-band
scale in Node-RED against live data and argues for it explicitly:

- **absolute** bands, not relative to the visible data set — his reasoning is
  that a relative scale prevents muscle memory, since a colour's meaning would
  shift from view to view. Convincing, and it settles the question.
- **four** bands, no more: beyond that the map gets messy and the colours stop
  being tellable apart.
- His cut: `>= 100` extreme, `>= 50` high, `>= 10` medium, `< 10` low.
- His colours: `#FF0000`, `#FF4D00`, `#FF7400`, `#FFC100` — red through orange
  to yellow, which drops straight into our marker's circle fill. Note the ramp
  also varies in lightness, so it does not depend on hue discrimination alone.
- He deliberately left confidence out of the classification.

That converts C from "blocked on a maintainer decision" to "blocked on nothing",
with thresholds that someone has already lived with. Still a maintainer call,
but now it is confirming a proposal rather than inventing one.

**K. Reverse geocoding — noted, not ours.** He is building a place-name lookup
for the nearest fire himself, off `nearest_entity_id`. Worth recording that the
v0.2.0 pointer is doing its job, but the feature itself would mean a third
external data source for a cosmetic gain. Leave it to users.

Also worth noting for G: he is not using the core map card but `auto-entities`
plus a third-party map, colouring markers through card config. Our
`entity_picture` route serves the core card; the two do not conflict.

## From the maintainer, second round (2026-07-28)

**L. Marker size — raised, and it cannot be done from here.** Fires close
together overlap on the map at low zoom; the proposal was to draw the icons
smaller. Checked against the frontend source (`ha-entity-marker.ts`) rather than
guessed, and the answer is that **the integration does not control marker size**:

```css
width:  var(--ha-marker-size, 48px);
height: var(--ha-marker-size, 48px);
border: 1px solid var(--ha-marker-color, var(--primary-color));
background-color: var(--card-background-color);
border-radius: var(--ha-marker-border-radius, 50%);
```

The picture we supply is painted into that box with `background-size: cover`
under `overflow: hidden`. Drawing our SVG smaller therefore shrinks the *flame*,
not the marker: what remains is a small flame inside an unchanged 48px disc that
still carries the card's background colour and a 1px border. Worse, not better.
The same reasoning kills per-fire size scaling — `--ha-marker-size` is a CSS
variable on the card, not a per-entity property, so size cannot carry FRP.

What is actually available is the variable itself, set by the user through a
theme or card-mod. That belongs in the README as a recipe, not in the code — it
is a per-dashboard taste decision. (Untested detail: CSS variables inherit
through shadow DOM, so setting it on the card should reach the markers, but that
wants one live check before it goes in the docs.)

Also worth separating cause from symptom: the crowding is density at low zoom,
not pixel size. **C is the better answer to it** — four clearly distinct colours
stay readable in a clump, where uniformly smaller icons just make every marker
harder to see, including the one that matters.

## What the data looks like (measured 2026-07-28)

Two areas run through the shipped pipeline, to check the bands against reality
rather than against intuition. Bordeaux is not a configured entry — it was
probed with the reference entry's own settings (150 km, 24 h, three satellites,
no filters) using `api.py` directly on the instance.

| | 43.60/3.90 (reference) | 44.84/-0.58 (Bordeaux) |
|---|---|---|
| detections after filtering | 92 | 216 |
| deduplicated fires | 9 | 32 |
| `extreme` | 0 | 0 |
| `high` | 0 | 1 (84.3 MW) |
| `moderate` | 2 | 5 |
| `low` | 7 (78%) | 26 (81%) |

Both are dominated by weak detections at almost the same ratio, which is what
the band split has to survive — and the argument for an absolute scale in one
number: relative to the visible set, today's 46.5 MW fire would be the reddest
thing on the reference map, and tomorrow, next to a real one, amber.

`extreme` (≥100 MW) did not appear in either area. That is the band working as
intended rather than a threshold set too high: the strongest fire in view is a
30-detection, three-satellite, high-confidence burn near Bordeaux at 84 MW, and
it should not be maxing out the scale.

The Bordeaux set also produced the argument that shaped **A**: six of its fires
sit between 20 and 27 km out in the same direction, some barely a kilometre
apart. Matching new clusters onto old ones therefore cannot be a plain greedy
pass in arbitrary order — a fire could be handed its neighbour's identity.

### How often the id problem actually bites

Waiting for a live refresh to demonstrate the drift does not work: FIRMS
returned byte-identical data across a full cycle, because the 24-hour window
only changes when a satellite passes over, not every 15 minutes. The drift was
therefore driven deliberately over the real detections of both areas, with the
expected pairing derived from position alone so the ids are never consulted.

Nudging every detection by 220 m — about what one new pixel does to a centroid
— **would have renamed 2 of the 9 reference fires and 9 of the 32 around
Bordeaux** before this release. With the carry-over, all of them kept their
identity, and across drift, a missing satellite and a newly appearing fire, in
both areas, **no id was ever misassigned or handed out twice**.

That is the number worth remembering: not a rare edge case, but roughly every
fourth fire in a busy area, on a movement too small to see.

## Proposed order

The forcing function is [hacs/default#9526](https://github.com/hacs/default/pull/9526):
it is open, all checks green, and it can be merged on any day without warning.
The moment it is, people arrive who have never read the forum thread. What
greets them is the README, and what trips them up is the unbounded radius. That
argues for doing the cheap protective work *first* and the big feature second,
even though the big feature is the more interesting one.

0. **I — the wind wording.** Ahead of the release entirely. One line of README,
   no version bump, and it removes a sentence a user has already read the wrong
   way.
1. **D + E — the arrival kit.** Small and both are silent-wrong-answer bugs, the
   worst kind for a first impression. D is a validator in the config flow plus a
   truncation flag surfaced on the sensor; E is one extra attribute in
   `geo_location.py:_update_from_cluster` plus a README line.
2. **C — FRP marker colour + intensity attribute.** Moved up: post #18 supplies
   the thresholds, so what is left is cheap — `MARKER_PICTURE` becomes a small
   function of FRP. It also answers, visibly, the person who is actively testing
   for us.
3. **A — stable cluster IDs.** Contained (`api.py` plus coordinator state, no
   UI), worth shipping on its own for the preserved history, and a hard
   prerequisite for B.
4. **B — manual ignore zones.** The actual headline of the release, and the
   largest item by some distance: Home Assistant has no native "list of
   locations" selector, so the options flow grows a menu with add/remove steps
   around a `LocationSelector`. The filtering itself is trivial (haversine
   against a list). Manual only — see the entry above.
5. **F — README / wiki split.** Prose, no code, no release risk, so it can run
   alongside any of the above and should land before the HACS merge.
6. **G (wind on the map), H, K — not in 0.4.0.** G needs the one-request rule
   settled first; H needs decomposing into real items; K stays with users.

Open maintainer decisions blocking the above: for **I**, the exact replacement
wording, since this is the safety-adjacent line the project has deliberately
policed; for **C**, whether to adopt pyspilf's bands as-is and whether the
attribute is `severity` or `intensity`; for **F**, the front-page/wiki cut.

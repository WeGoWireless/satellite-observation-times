# v0.5.0 — candidate list, and the two releases behind it

Started as a collection stage. **Worked through with the maintainer on
2026-07-29**, and the result is a cut across three releases — 0.5.0 arrival,
0.6.0 relevance, 0.7.0 time. What was decided is marked as decided; the
reasoning is kept because most of it is the kind that gets re-litigated
otherwise. Split this file per release once 0.5.0 ships.

Context check on 2026-07-29: still **no GitHub issues and no PRs** — every piece
of feedback this project has ever had arrived through the forum thread. The
thread has grown from 19 to **30 posts** since the v0.4.0 list was written, and
the composition changed: `magicbeing` and `Mariusthvdb` are the first people to
show up who did *not* follow the development, installed from the announcement,
and reported what happened. That is the audience the HACS default store will
deliver, and it moves the list.
[hacs/default#9526](https://github.com/hacs/default/pull/9526) is still open.

## What v0.4.0 closed

A (stable cluster ids), B (manual ignore zones), C (FRP marker colour +
`intensity`), D (500 km radius cap + `truncated`), E (`origin` attribute),
I (the wind wording). Do not re-open them here.

**F (README → wiki) is proposed closed as "done differently."** The recipes
moved to `docs/dashboard.md` and `docs/templates.md`, the README went 412 → 183
lines, and the files ship with the tag that produced them — which is exactly
the property a wiki would have cost. No wiki.

## From the thread (posts 20–30, 2026-07-28)

**A. `wind_speed` has no unit, and a reader supplied the wrong one.**
pyspilf (#20) reported Developer Tools showing `4.4` while the dashboard card
said `16 km/h`, reloaded everything, and asked what he was doing wrong. Both
numbers are one reading: met.no delivers m/s, the card multiplies by 3.6. His
own diagnosis in #22 is the important part — *"what threw me off was the
attribute showing unit of measurement km right under the wind"*: the sensor's
own unit (km, for the distance) sits directly under the wind attributes in the
states view, and the eye carries it over.

This is precisely the defect class the project has been policing since D: a
plausible-looking number that is wrong, with nothing about it looking wrong. A
practising engineer misread it in the first hour. It is not a documentation
problem — the README does say m/s.

Three shapes to choose from:

1. **Wind speed becomes its own sensor entity** (`device_class: wind_speed`,
   native unit m/s). Home Assistant then prints the unit, converts it to the
   instance's unit system, and lets the user override it per entity — the
   ambiguity disappears structurally rather than by wording. Also gives history
   and a graph, which an attribute cannot. Costs one more entity per entry that
   is `unknown` whenever there is no fire. *Verify the conversion behaviour
   against the HA version in `hacs.json` before committing to this.*
2. **Keep the attribute, add the unit to its name** (`wind_speed_ms`). Cheapest,
   unambiguous, and a breaking change for anyone who copied a template.
3. **Convert the attribute to the instance's unit system.** Rejected on sight:
   it makes the same attribute mean different things on different instances,
   and it silently double-converts every card that already multiplies by 3.6 —
   including the one in our own docs.

Option 1 is the recommendation. Whether the existing attribute stays alongside
it (compatibility, and templates do want the raw number next to `bearing`) is
the maintainer decision. Note the same question exists for `bearing`,
`wind_bearing` and `frp_mw` — they are unitless numbers on a sensor that
displays km — but nobody has misread those, so this is not an argument for
converting the whole attribute set into entities.

**B. A new user got entities and no map, then found the map himself.**
magicbeing (#24): *"I have it installed and have some data displaying (nearest
fire etc) but no map. Is there a step needs adding to the HACS instructions?"*
Answered and already fixed in the docs — the map card is a setup step now, in
the README and in the thread's first post. What is *not* fixed is the shape of
the problem: the integration ships entities, and Home Assistant builds nothing
out of them, so a correct install looks broken.

Two threads out of this, both cheap:

- **He found the fires on the pre-installed Map panel himself** (#27:
  *"clicked on the pre installed Map on the sidebar. Bingo!"*). That is a
  zero-configuration answer to "where are my fires", it is user-verified, and
  it is nowhere in our docs. One paragraph in the setup section.
- **He then asked for the next two things by name** (#27): a view that holds
  the map and the sensors together, and *"setting up an alert for when a hotspot
  is within a certain distance"*. The second one is the entire point of the
  integration and today it is a template in `docs/templates.md` that he has to
  copy, adapt and debug.

**C. A proximity-alert blueprint.** The natural answer to B, and the first item
here that a newcomer would actually notice. An automation blueprint with the
distance threshold, the entry, and the notification target as inputs, published
in the repo with a one-click *Import blueprint* link. No integration code, no
release coupling, testable on the live instance.

The design line applies to the blueprint text as hard as it applies to the card:
the notification says how far and in which direction, not what to do about it.
"Fire 8 km NE of home, wind pushing the smoke towards you" is a fact.
"Evacuate" is not ours to say. Worth deciding up front whether the blueprint
may mention the wind at all, or stays with distance only.

**D. pyspilf's auto-entities + custom map-card config (#30).** He posted a
working card that filters `geo_location.wildfire_hotspot_*` by the `intensity`
attribute into four `z_index_offset` layers, so extreme fires draw on top. It
confirms the v0.4.0 design decision — `intensity` exists so cards can filter
without repeating thresholds, and someone did exactly that within a day. Belongs
in `docs/dashboard.md` as a recipe, with his API key stripped and with his own
caveats kept: the custom card needs `theme_mode: light` to render dark, and
`display: icon` overrides our marker picture.

**E. GDACS has no fire category (#23, #26).** Mariusthvdb came looking for why
GDACS never alerted him for the fires next door; the answer is that GDACS covers
drought, earthquake, flood, cyclone, tsunami and volcano, and nothing else. He
then found wildfire *models* on the new GDACS site. Positioning, not a feature —
at most one line in the README's comparison table. Do not turn it into a
competitive claim, and do not use his nearby fires as marketing (editorial rule).

## Verified while checking his asides (2026-07-29)

Post #30 carries two remarks he did not mean as reports. Both were checked
against the frontend source on `dev` before being planned around.

**V1. Dark mode does not invert our markers — nothing to do.** He writes that his
card needs `theme_mode: light` or Home Assistant inverts it. `ha-map.ts` puts
the invert filter on `.leaflet-tile-pane` only; markers live in
`.leaflet-marker-pane`, a sibling. Our band colours render as authored in both
themes. His workaround belongs to his card and must not be copied into our docs.

**V2. The recommended card hides the v0.4.0 colours — and this one is real.**
The core map card clusters by default (`cluster ?? true`) and merges markers
within 40 px into a single `--primary-color` disc with a count. At the
`default_zoom: 8` our own README prints, 40 px is about **18 km** at 43.6° N. So
in the situation the integration exists for — several fires in the area — the
four intensity colours collapse into one blue bubble with a number on it.

Three consequences, all documentation:

- `cluster: false` belongs in the recommended card, with one line saying why.
  It shows every fire in its own colour and costs clarity when there are many —
  a real trade-off, so say both halves.
- **The option only exists from HA 2025.6** (frontend #25429). Clustering itself
  arrived in 2025.3 (#24244), so anyone between 2025.3 and 2025.5 gets it with
  no way out. `hacs.json` currently claims 2025.1.0 — decide whether to raise
  the floor or to footnote it.
- **The built-in Map panel always clusters.** It renders `<ha-map>` without
  `clusterMarkers` and exposes no setting. That is the route magicbeing found
  by himself (#27), so if B recommends it, it has to say what it does and does
  not show.

**V3. With clustering off, the strongest fire is not on top.** `DecoratedMarker`
extends Leaflet's `Marker` and nothing in the frontend sets `zIndexOffset`, so
z-index follows the marker's y pixel position: **the southernmost fire covers
the ones behind it**, whatever its intensity. Not reachable from the
integration — the card decides. This is what pyspilf's `z_index_offset` layers
buy him, and it is the honest reason to point dense-area users at his recipe.

## Carried over from the v0.4.0 list

**G. Wind on the map.** Unchanged and still blocked on the same decision: wind
is fetched for the nearest fire only, one met.no request per cycle, so either
one marker can carry an arrow or the rule gets renegotiated (N nearest, or one
regional lookup for the whole box). Post #30 adds a wrinkle — users on
`auto-entities` + a custom map card override our picture entirely with
`display: icon`, so the drawing work only reaches core-card users. Decide the
request rule before any drawing.

**H. `days_seen` on a fire.** The half of the ignore-zone story that was left
out: expose "this spot has been detected on N separate days" as a fact so a user
can *find* the factory that needs a zone, without the integration ever deciding
a fire is not a fire. The prerequisite shipped in v0.4.0 (ids now survive
drift), but the carry-over is memory-only and resets on every reload — so this
needs persisted state (`Store`), which is the same machinery that would let
cluster ids survive a restart. Two features, one piece of plumbing.

**I. Configuration and general UX.** Still the vague umbrella it was, and it has
to be broken into verifiable items or dropped. Concrete candidates that fell out
of this round: the options menu now has filters and zones but no way to see what
a filter is currently costing you; there is no "test my key" feedback beyond
success; nothing tells a user their radius is bigger than their data.

**J. Marker size recipe.** `--ha-marker-size` through a theme or card-mod, as a
docs recipe — the integration cannot set it. Needs one live check that the
variable actually reaches the markers through the shadow DOM before it is
written down.

**K. Reverse geocoding.** Stays with users. Unchanged.

## Arrival kit for the HACS default store

None of this is user-visible, all of it is what strangers filing bug reports
will need. The forum thread has been a workable support channel for four people
who know the project; GitHub issues from people who do not are a different
volume and a different quality of report.

**L. `diagnostics.py`.** Home Assistant standard, expected by Core, ~50 lines:
config entry, options, per-satellite counts, cluster count, last error — with
the MAP_KEY redacted. Turns "it doesn't work" into something answerable.

**M. Issue templates.** `.github/` has a funding file and one workflow and
nothing else. A bug template that asks for the diagnostics dump, the HA version
and the integration version costs one file.

**N. Repair issues instead of silent attributes.** `truncated` and
`satellite_errors` are attributes nobody looks at. `ir.async_create_issue` puts
them in the repairs dashboard with a sentence saying what to do (shrink the
radius). Small, HA-native, and it is the third time the "silently too low"
failure mode has come up.

**O. Test harness (`pytest-homeassistant-custom-component`).** The smoke test
covers `api.py` only. v0.4.0 touched the coordinator, the config flow and both
platforms, and all three are verified by hand on one live instance. With a wider
audience this stops scaling — and the harness is a prerequisite for the Core
submission anyway. Too big to swallow whole; the first slice would be the config
flow and the coordinator.

## From the brainstorm (2026-07-29)

Four ideas that are not in anyone's post. They come out of one observation: the
integration knows everything about *where* and nothing about *when*. A fire
found twenty minutes ago and one that has warmed the same spot for three days
look identical on our map, and three separate open items turn out to be the
same missing piece.

**N1. Every fire carries an age.** When we first saw it, and on how many
separate days it has appeared. This is `days_seen` (the factory question) and
"is this new?" (the human question) from one mechanism. Needs state that
survives a restart — the id carry-over currently lives in memory only, so this
is the largest single piece of work on any of these lists.

**N2. A "new fire" signal for automations.** The defect it fixes: an automation
on "distance below 10 km" fires once. If the nearest fire already sits at 8 km
and a new one appears at 5, the sensor goes 8 → 5 and never crosses the
threshold again — **no alert, in exactly the situation that matters**. An
`event` entity (the platform exists since HA 2023.8; the exact shape wants
checking against Core conventions) carrying distance, bearing and intensity
makes the alert reliable and the blueprint simpler. Depends on N1: without the
age memory there is no "new".

**N3. Derive the FIRMS region from the coordinates.** The setup asks for it, and
the user drags a pin onto a map immediately afterwards — we know the answer.
Picking the wrong region yields no data and no explanation, which is the same
silent-wrong-answer class as D and V2. One field less is one failure less.
Verify against `config_flow.py` that the mapping is really that simple.

**N4. The situation in words.** At thirty fires the map fails in both settings
(see V2/V3), and a sentence — "7 fires in range, nearest 12 km NE, 2 of them new
since this morning" — beats it. Docs recipe, not code, and it only pays once N1
exists. Parked for now.

## The cut (decided 2026-07-29)

**0.5.0 — arrival.** Small, fast, no persisted state. Everything here is aimed
at the person who installs from the HACS default store having read nothing.

1. **V2 + V3 — the card recommendation.** `cluster: false` in the recommended
   card with the trade-off stated, the Map panel described honestly, the draw
   order noted. Plus the `hacs.json` floor, now decided.
2. **A — the wind speed unit**, as its own sensor, with the attribute kept.
3. **N5 — `bearing` and `direction` on every fire entity.** See "the wind's
   reach" below. Already computed for every cluster in `cluster_hotspots`
   (`api.py`) and published for the nearest one only — two attributes, no new
   data, no new request.
4. **N3 — the region field**, if the config flow allows it.
5. **C + B — the proximity blueprint and the two onboarding paragraphs.**
   Shipped in its threshold form, with the N2 limitation written down, and
   replaced in 0.6.0. Waiting two releases would leave magicbeing with nothing.
6. **L + M + N — the arrival kit.** Diagnostics, issue templates, repairs.
7. **D + E + J — recipes.** pyspilf's card, the GDACS line, the marker size
   note (needs one live check first).
8. ~~**`daynight` is always empty — find out why.**~~ **Answered and removed.**
   The layer schema declares the field, the GeoJSON never carries it. Probed on
   2026-07-29 across VIIRS SNPP, NOAA-20 and MODIS, 24 h and 7 d, in Europe, the
   USA and Australia — absent from the property list every time. Not a parsing
   bug on our side and nothing to fix: the attribute is gone from the code and
   the README. It was `None` in every release up to v0.4.0, so nothing can be
   depending on it.

**0.6.0 — relevance.** The release that answers *which fire actually concerns
me* — without the integration ever deciding it. The maintainer's case: the
nearest fire can be a small one 25 km out while a far bigger one at 40 km is the
one the wind carries towards you. "Nearest" is a poor proxy for "matters", and
it is the only ranking we offer today. Needs no persisted state, which is why it
comes before 0.7.0.

1. **N7 — wind for the N nearest fires, N configurable.** `MetNoClient` holds
   exactly one forecast by design, so this is a cache rewrite plus one option.
   The option is legitimate under this project's own convention: it changes the
   number of API calls, exactly like the satellite choice. Budget arithmetic and
   the met.no exposure it creates are under "the wind's reach".
2. **N8 — `smoke_offset` on every fire that has a wind reading.** The angle
   between the direction the wind pushes the smoke and the line from that fire
   to you. It stands to `wind_bearing` exactly as `intensity` stands to
   `frp_mw`: the finished number, so no card or automation has to carry the
   thresholds. Absent — not `None` — on fires with no reading.
3. **N6 — the action that returns the wind at one named fire.** Costs nothing
   until called, and reaches the fire that falls outside the budget.
4. **Docs.** What the budget covers and what it misses, and the sentence that
   decides how this reads: **this is geometry, not danger.** A fire drifting
   away is not a fire that is safe, and `smoke_offset` is not a threat level.

With this, the user builds the rule the integration refuses to build: the
blueprint fires on "fire within X km **and** `smoke_offset` under 60°", the map
shows only what is drifting your way. We supply the number, the user judges —
the same move that made `intensity` right.

**0.7.0 — time.** One theme, one piece of plumbing, and the first state this
integration has ever kept across a restart.

1. **Persisted cluster state** — the `Store` layer everything below sits on.
2. **N1 — `first_seen`, age, `days_seen`**, shipping with the README paragraph
   on why there is no automatic ignore.
3. **N2 — the new-fire signal**, and the blueprint rebuilt on it.
4. **N4 — the situation-in-words recipe**, which only works once N1 is there.

**The alert is only finished after 0.7.0.** "Tell me when a **new** fire appears
that is drifting towards me" needs both halves: 0.6.0 supplies *drifting towards
me*, 0.7.0 supplies *new*. In between, the alert can repeat for a fire the user
already knows about. That is the accepted cost of taking relevance first.

**Note before 0.7.0 starts:** it is the first release whose logic outlives a
restart, and `tests/smoke_test.py` covers `api.py` only. Either the smoke test
grows a persistence section or the first slice of O (a real test harness) comes
first. Do not ship a memory across restarts that nothing tests.

**Parked, with reasons already written down:** G (wind on the map — needs the
one-request rule settled), K (reverse geocoding — stays with users), the Core
submission (the integration is eleven days old and still changing shape every
week), a third data source of any kind, and any form of risk score.

## Decided (2026-07-29)

- **The `hacs.json` floor rises to 2025.6**, so `cluster: false` always exists
  and the recommended card cannot silently hide the intensity colours. Locking
  out 2025.1–2025.5 costs nothing real: those releases are eighteen months old
  by now and Home Assistant ships monthly.
- **The blueprint's notification may name the wind**, under the card's rules:
  the thirds at 60°/120°, the raw angle alongside the words, no verdict. Two
  constraints fall out of it. The wind is only ever known for the **nearest**
  fire, so the message has to read cleanly when there is none — not "wind
  unknown" bolted onto a sentence built around it. And a push notification has
  room for one sentence, not for the card's caveat line; the caveat therefore
  belongs in the blueprint's description, which the user reads while setting the
  alert up rather than while it goes off.

- **`wind_speed` stays as an attribute**, and the sensor comes in addition. Every
  template this project has published reads the attribute, as does every user
  copy of one. The ambiguity is cured by the sensor existing, not by deleting
  the raw number. The docs describe the attribute explicitly as the raw m/s
  value from met.no, and the example card moves to the sensor — so the raw
  number becomes something you look for rather than something you trip over.
- **N1 ships with the explanation.** Publishing "seen on 14 days" gives a user
  the observation they need to find their own factory. It also makes the
  rejected automatic version look overdue, so the README says up front why it
  will not come — the argument already exists, one paragraph up, under ignore
  zones. Same shape as the wind: we supply the observation, the user judges.

## The wind's reach (raised 2026-07-29)

The question: wind is fetched for the **nearest** fire, but the nearest fire may
be a small one while a bigger fire a kilometre further out is the one drifting
towards you. Should the user be able to choose which fire the wind describes?

**The physics answers most of it.** Two fires a kilometre apart do not have
different wind. We round coordinates to two decimals before asking (~1 km), so
both land on the same cache key and get literally the same forecast — and
met.no's own grid outside Scandinavia is coarser still. *(Worth confirming
before that number goes into the docs.)* So what differs between those two
fires is not the wind. It is **the direction each one lies in from you**, which
decides whether that same wind carries smoke towards you or past you.

And that is a gap we can close for nothing: `cluster_hotspots` computes
`bearing` and `direction` for **every** cluster, and `geo_location.py` publishes
neither — only the nearest-hotspot sensor exposes them, for the nearest fire.
Put the two attributes on every fire (**N5**, in 0.5.0) and the one wind reading
becomes usable for any fire near enough to share it. The README's
upwind/downwind template then works per fire instead of only for the closest.

**What stays unsolved by that** is the case the maintainer actually meant: a
small fire 25 km out, and a much bigger one at 40 km that the wind is carrying
towards you. Forty kilometres is several model cells. Applying the near fire's
reading to the far one would be the same plausible-looking wrong number this
project has deleted three times. **Per-fire wind has to be per-fire** — hence
N7, and hence 0.6.0.

*Correction to the cheap idea above:* deduplicating requests by grid cell saves
less than it first looks. Our own clustering already holds fires at least a
kilometre apart (`CLUSTER_RADIUS_KM`), which is about one cell. Budget in fires,
not in cells: **one request per fire.**

**The budget at "wind for the 5 nearest":** roughly 10 requests an hour per
instance once the `Expires` cache absorbs the repeats. At a thousand
installations that is about 3 a second, all under one User-Agent, against
met.no's stated 20/s threshold. Workable — and the first point at which an
outside organisation notices this project. Two consequences: N is capped and
configurable, and the docs say plainly that a fire ranked beyond N carries no
wind reading. A budget is a budget.

**On a second weather source (raised 2026-07-29, deferred).** Resolution is not
the problem — coverage is, and a finer grid does not reduce the request count.
Volume is a real argument though: **Open-Meteo** needs no key, allows far more
requests, and serves regional fine-scale models — AROME at ~1.3 km over France,
against the ~9 km met.no has outside Scandinavia. *(Terms, limits and both
resolution figures unverified — check before any of this reaches the docs.)*
Deferred deliberately: a source swap costs the client, the tests, and the CC-BY
attribution baked into code and docs. Build the budget on met.no, measure it,
and switch only with numbers in hand.

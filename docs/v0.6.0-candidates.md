## New since the release

### P. The docs say km, the screen does not always say km (RedKing, #32)

> **Shipped as v0.5.1** on 2026-07-29, ahead of this release — see
> [`release-notes-v0.5.1.md`](release-notes-v0.5.1.md). The rest of this section
> is the finding as it was written up.

> *"I'm getting distances in kilometers. How do I change that to miles? Is it
> because my HA unit system is set to Celsius/Kilos?"*

His own guess is right, and the answer to him is one sentence: the nearest
hotspot sensor carries `device_class: distance`, so Home Assistant follows the
instance's unit system, and the unit can also be overridden per entity in the
entity settings. No code needed for **his** question.

**The problem is what happens after he does it.** Verified against Home
Assistant `dev`:

- `US_CUSTOMARY_SYSTEM` maps `("distance", KILOMETERS) → MILES`, and
  `SensorEntity._get_initial_suggested_unit` consults that when the entity is
  first registered. So on a US instance `sensor.<name>_nearest_hotspot` has
  been reading **miles** since v0.1.0. Same for the per-entity override, which
  wins over everything.
- The `geo_location` fire entities cannot follow. `GeolocationEvent` is not a
  sensor, `_attr_unit_of_measurement` is hard-set to kilometres, and no
  conversion applies. **They stay km on every instance.**
- Everything we have written assumes km, in the two places where the number is
  printed next to a unit:
  - `blueprints/.../fire_within_distance.yaml` — `Fire within {{ limit }} km`
    in the title and `{{ states(sensor) }} km` in the message, plus the
    threshold input labelled `unit_of_measurement: km` while the trigger
    compares against the *displayed* state.
  - `README.md:119`, `docs/templates.md` (4 recipes), `docs/dashboard.md` (the
    card).

So a US user who installs from the HACS default store, imports the blueprint
and sets 10 gets an alert at 10 **miles** that says **km**, and a card next to
a map whose markers read km. Every number is plausible and the label is wrong —
the exact defect class this project has deleted three times (the radius cap,
the wind speed, the region name). The irony is that `docs/templates.md:46`
already explains the mechanism for the *wind* sensor; nobody carried it across
to the distance.

**Worth fixing, and it is small.** The fix is to stop hard-coding the unit and
read it from the entity:

```jinja
{{ states(sensor) }} {{ state_attr(sensor, 'unit_of_measurement') }}
```

That is correct on every instance and for every override, in the blueprint and
in every recipe. The threshold input loses its `km` label and gains a sentence
saying it is in whatever the sensor shows — which is also what the trigger has
always compared against. The `geo_location` km stays and gets one line in the
README saying so, because it cannot be changed from here.

**One consequence to write into the release notes:** a blueprint is copied into
the user's config at import. Existing automations keep the old text until the
user re-imports it. There are at most a handful of them today, which is an
argument for fixing it now rather than after the default store lands.

### R. The integration itself as something to monitor (pyspilf, #35)

The first post in this project's history that is not about fires but about
**running the thing**: a watchdog on whether the data is still arriving. That is
the audience the default store delivers, and it is worth reading as a category
rather than as four wishes.

**R1. A pointer on `max_fire_radiative_power`.** He wants the sensor to say
which fire the value came from, the way `nearest_entity_id` does. Cheap: the
coordinator holds the cluster when it takes the maximum, and the
`cluster_id -> entity_id` register has existed since v0.2.0 for exactly this.
Same `attributes_fn` pattern, roughly eight lines. **Into 0.6.0.**

His alternative — a separate "most intense hotspot" entity with a full
attribute set — is the one to decline, and the reason is in this release:
`smoke_offset` adds a third ranking. One entity per ranking means three sensors
duplicating the same eight attributes. A number plus a pointer to the fire that
carries everything else is what scales. Note *why* he asked, though: he arrived
at "nearest is not the only interesting ranking" on his own, which is the
premise this entire release rests on.

**R2. What `satellite_errors` holds.** A question, not a request. From the code:
one entry per satellite whose fetch failed, carrying the message — timeout
(60 s), connection error, HTTP other than 200, or a response that is not
GeoJSON. So yes, a FIRMS timeout lands there. Two things that are not obvious
and belong in the docs: a rejected MAP_KEY (401/403) does *not*, it raises
`ConfigEntryAuthFailed` and starts the reauth flow; and when *every* satellite
fails there is no attribute to read, because the coordinator raises
`UpdateFailed` and every entity goes `unavailable`. Partial failure shows in the
attribute, total failure in the state. **Docs.**

**R3. A timestamp for "data last arrived" — Home Assistant already has it.**
Since 2024.7 there are three timestamps, not two: `last_changed` (the value
changed), `last_updated` (value or attributes), and **`last_reported`** — every
report, including an identical one. `StateMachine.async_set` refreshes
`last_reported` and fires `EVENT_STATE_REPORTED` when state and attributes both
match, instead of skipping the write. That is precisely the case he anticipates
("data may be retrieved but nothing changed in it").

Measured on the live instance while checking: `last_changed` 7.2 h,
`last_updated` 2.5 h, `last_reported` 14.6 min — the cycle that had just run.

So the answer is a recipe, not an attribute, and the recipe is the better
product: an attribute changing every 15 minutes would write a state change every
15 minutes, while an identical report writes nothing to the recorder at all.
**Docs** — a watchdog template plus the `unavailable` trigger for a hard outage.
If an entity is ever wanted anyway, Core's `TimestampDataUpdateCoordinator`
carries `last_update_success_time`; it is a base-class swap and nothing more.

**R4. The observability compliment** is not a work item, but it is the
confirmation that `raw_detections`, `per_satellite`, `truncated` and the v0.5.0
repair notice were the right line to hold.

## The 0.6.0 cut, checked against the code

### N7 — wind for the N nearest fires

Today `FirmsCoordinator._async_wind` asks for the nearest cluster only, and
`MetNoClient` holds exactly one forecast (`self._key`, `self._payload`,
`self._last_modified`, `self._valid_until`). The work:

- **`MetNoClient` gets a keyed cache.** One entry per rounded coordinate pair
  instead of one entry total, evicted by least-recent use, capped a little
  above the maximum N.
- **The rate-limit backoff must become global, not per key.** Today a 403/429
  sets `_valid_until` for the key that was being fetched. With several keys in
  play, a throttled client would move straight to the next fire and keep
  firing — precisely what earns the permanent ban the comment there warns
  about. One `_blocked_until` for the whole client, checked before any request.
- **The coordinator loops** over the N nearest clusters, sequentially rather
  than gathered: five requests in a burst are five requests in a burst, and
  nothing here is latency-critical. It stops early once the client is backed
  off.
- **`FirmsData.nearest_wind` becomes a mapping** `cluster_id -> WindObservation`
  with `nearest_wind` kept as a property, so the sensor, the diagnostics and
  every published template keep working unchanged.
- **One option** in the options flow (`wind_fires`), default 3, capped at 5,
  plus `strings.json` and both translations.
- **Smoke test:** the current met.no section tests a single-slot cache
  explicitly ("moving to another fire refetches", "and drops the stale
  If-Modified-Since"). Those tests describe behaviour that is about to change
  and have to be rewritten, not just extended.

Budget, from the 0.5.0 paper: at the default of 3 and the cap of 5, single
digits of requests an hour per instance once `Expires` absorbs the repeats; at
a thousand installations a few a second against met.no's stated 20/s threshold.
The cap and the option exist because of that number, and the docs say plainly
that a fire ranked beyond N carries no wind reading.

### N8 — `smoke_offset` on every fire that has a wind reading

The angle between the direction the wind pushes the smoke and the line from
that fire to you. `0°` means the smoke is coming straight at you, `180°`
straight away.

The arithmetic is already in the blueprint and reduces to `wind_bearing -
bearing`, normalised to ±180 and taken absolute: the smoke travels along
`wind_bearing + 180`, the line from the fire to you is `bearing + 180`, and the
two offsets cancel. It belongs in `api.py` next to `cardinal()` as one small
function, so the blueprint, the card recipe and the attribute all read the same
number instead of three copies of the same expression.

It stands to `wind_bearing` as `intensity` stands to `frp_mw` — the finished
number, so no card carries the thresholds. It ships alongside `wind_bearing`,
`wind_direction` and `wind_speed` on the same fire, so the number can be
checked against the reading it came from. All four are absent, not `None`, on
fires without a reading, per the 0.5.0 decision.

### N6 — an action that returns the wind at one named fire

`SupportsResponse.ONLY`, takes a fire entity id, returns bearing, direction,
speed and `smoke_offset`. Costs nothing until called and reaches the fire that
falls outside N. New file (`services.yaml`), new strings, and the first action
this integration has ever published.

### R1 — the pointer on the max-FRP sensor

Eight lines, the pattern already exists, and it comes from the one user running
this as infrastructure. Rides along with this release rather than waiting for a
theme of its own.

### Docs

Three additions beyond the release's own theme, all from R: what
`satellite_errors` holds and what it does *not* hold, the `last_reported`
watchdog recipe, and the `unavailable` trigger for a total outage.

The sentence that decides how the whole release reads: **this is geometry, not
danger.** A fire drifting away is not a fire that is safe. `smoke_offset` is a
number, not a threat level. Plus what the budget covers and what it misses.

## Decided (2026-07-29)

- **P ships first, as v0.5.1.** A wrong label on a right number is live, and
  the smaller the audience is when it gets fixed, the fewer blueprint copies
  carry it. Done.
- **N defaults to 3, capped at 5.** At `1` the release would do nothing for
  anyone who does not go looking for the option, and relevance is the point of
  it. Three fires is roughly 12 requests an hour per instance before the
  `Expires` cache absorbs the repeats — about 3 a second at a thousand
  installations, against met.no's stated 20/s threshold. The cap is where that
  arithmetic stops being comfortable, not where the feature stops being useful.
- **A fire with a reading carries all four attributes**: `smoke_offset`,
  `wind_bearing`, `wind_direction`, `wind_speed`. Same shape as the
  nearest-hotspot sensor, and it keeps the project's own move intact — we
  publish the observation and the finished number, the user checks it and
  judges. `smoke_offset` alone would be a number nobody can verify. The
  standing "add fewer attributes" rule is about attributes nobody asked for;
  these are the ones the release exists for.

Still open: **Q — where feature requests go**, and who says so where.
